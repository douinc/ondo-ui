# Ondo UI npm release automation

## Goal

Make `@dou.so/ondo-ui` a small, independently publishable CLI package and
automate semantic versioning, package changelogs, release PRs, and npm
publishing while keeping the Ondo UI documentation site deployment separate.

## Constraints and current state

- The repository root is the Next.js/Fumadocs documentation site.
- The current root package is named `@dou.so/ondo-ui`, is version `1.3.1`, and
  contains the CLI under `bin/`; publishing the root also exposes the site's
  runtime dependency graph.
- The CLI uses Node built-ins and should not need the site's dependencies at
  runtime.
- The existing `components.json` modification is user-owned and must not be
  reverted or included in an unrelated release-automation change.
- Existing bilingual MDX changelog pages are documentation content and should
  remain separate from the npm package's generated `CHANGELOG.md`.

## Implementation sequence

### 1. Establish the package boundary

- Mark the root site package private and remove its publishable-package
  metadata/bin entry so an accidental root publish cannot publish the site.
- Create `packages/ondo-ui-cli/package.json` for `@dou.so/ondo-ui` with the
  current public version, public access, exact GitHub repository metadata,
  package homepage, CLI bin mapping, and a narrow `files` allowlist.
- Move/copy the CLI entrypoint and package READMEs into that package, updating
  the existing CLI regression test to exercise the canonical entrypoint.
- Keep the package dependency-free apart from Node's built-ins.
- Add a package-level dry-run/contents check so a packed tarball contains only
  the intended CLI files and does not contain the documentation site's
  dependencies or source tree.

### 2. Add Changesets

- Add `@changesets/cli` and `@changesets/changelog-github` as root development
  dependencies.
- Add `.changeset/config.json` targeting the `douinc/ondo-ui` GitHub repository,
  public package access, and `main` as the base branch.
- Add scripts for creating changesets, applying versions, and publishing.
- Document the release contract: patch for fixes, minor for additive features,
  major for breaking changes; the next additive release after `1.3.1` is
  `1.4.0`.
- Configure Changesets to generate the CLI package's npm `CHANGELOG.md` and
  release PR notes. Do not attempt to generate the site's Korean/English MDX
  pages automatically in the first iteration.

### 3. Add CI release workflow

- Keep the existing site deploy workflow unchanged and add a dedicated
  `.github/workflows/release.yml`.
- On pushes to `main`, run install, tests, lint/typecheck, build, and package
  dry-run checks before invoking `changesets/action`.
- Grant only the permissions needed for release PRs and npm provenance:
  `contents: write`, `pull-requests: write`, and `id-token: write`.
- Use a current Node/npm version compatible with npm trusted publishing and
  publish the package through Changesets with the stable `latest` tag.
- Let Changesets open/update a release PR first; after that PR is merged, the
  next main push publishes the version and generated changelog.

### 4. Document the one-time external setup

- The package owner must configure npm Trusted Publishing for
  `@dou.so/ondo-ui` using GitHub Actions, repository `douinc/ondo-ui`, and the
  exact workflow filename `.github/workflows/release.yml`.
- The npm organization/package permissions must allow the account to configure
  the trusted publisher. No long-lived npm token should be committed.
- The package owner must merge the first Changesets release PR and verify the
  package's npm provenance after the publish job succeeds.

## Verification

- `bun install --frozen-lockfile` (or the repository's equivalent lockfile-safe
  install).
- `bun test`.
- `bun run typecheck` and `bun run lint`.
- `bun run build` after the MDX source cache is generated by postinstall.
- `npm pack --dry-run` from `packages/ondo-ui-cli` and inspect the file list.
- Run the CLI's existing tests and, where possible, smoke-test `npx`/`bunx`
  against the packed tarball in temporary consumer projects.
- Confirm the release workflow has no publish step until npm Trusted Publisher
  configuration is complete.
